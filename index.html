2.1 What software actually is, and how it's built

Software is instructions running on hardware to produce useful behavior. As a QA engineer you almost never test "software" in the abstract — you test applications: web apps, mobile apps, or APIs, each with predictable moving parts. Understanding those parts is what turns you from someone who can click around and notice things look wrong into someone who can reason about where a bug is likely to live.

2.2 Client-server architecture

sequenceDiagram
    participant U as User (Browser/App)
    participant C as Client (Frontend)
    participant S as Server (Backend)
    participant D as Database

    U->>C: Clicks "Login"
    C->>S: HTTP POST /api/login {email, password}
    S->>D: SELECT * FROM users WHERE email = ?
    D-->>S: User row (hashed password)
    S->>S: Compare password hash
    S-->>C: 200 OK + auth token
    C-->>U: Redirect to dashboard
  • Client: what the user directly interacts with — a browser rendering HTML/CSS/JS, or a mobile app.
  • Server (backend): receives requests, applies business logic, talks to the database, returns a response.
  • Why QA needs this: almost every bug you'll triage is really the question "is this a frontend bug (wrong thing displayed/sent) or a backend bug (wrong thing computed/stored)?" You can't write an accurate bug report without being able to at least guess the answer, and you certainly can't do API testing without understanding that the API is the server side, tested directly, bypassing the client.

2.3 Frontend vs. backend, web vs. mobile

Frontend Backend

Web apps run in a browser (no install). Mobile apps are installed (native — Swift/Kotlin, or cross-platform — React Native/Flutter). As QA you'll mostly test web apps and their APIs at entry level in BD; mobile testing (if it comes up) adds device/OS fragmentation as a new axis of testing (see Part 6, compatibility testing).

2.4 APIs — the concept, before the testing

An API (Application Programming Interface) is a defined contract that lets one piece of software ask another for data or action, without needing to know how the other one works internally. A REST API is the dominant style: it uses HTTP, treats things as "resources" (e.g., /users, /orders/42), and uses HTTP methods to say what you want to do to that resource. You'll go deep on this in Part 15 — for now, just internalize: the API is the backend's front door, and testing it directly (skipping the UI) is often faster and more precise than clicking through screens.

2.5 HTTP / HTTPS and the request-response cycle

HTTP (HyperText Transfer Protocol) is the language browsers and servers speak to each other. HTTPS is the same thing, encrypted (via TLS/SSL) — this matters for security testing (Part 19) because unencrypted HTTP means anyone on the network can read the traffic, including passwords.

Every interaction is a request (from client) and a response (from server):

Request:
  GET /api/products/17 HTTP/1.1
  Host: shop.example.com
  Authorization: Bearer eyJhbGciOi...

Response:
  HTTP/1.1 200 OK
  Content-Type: application/json

  {"id": 17, "name": "Wireless Mouse", "price": 850, "in_stock": true}

2.6 Common HTTP status codes Must Master

Range Meaning Examples you must know
2xx Success 200 OK, 201 Created, 204 No Content
3xx Redirection 301 Moved Permanently, 304 Not Modified
4xx Client error (you did something wrong) 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity
5xx Server error (the backend broke) 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable
Interview trap

401 (Unauthorized) actually means "not authenticated" — you don't know who this is. 403 (Forbidden) means "I know who you are, and you're not allowed." Mixing these up is a very common junior mistake and interviewers know to probe it.

2.7 JSON

The standard data format for APIs. Key-value pairs, nested objects, arrays:

{
  "user": {
    "id": 5,
    "name": "Shahed",
    "roles": ["tester", "admin"],
    "active": true,
    "last_login": null
  }
}

You need to read this fluently — API testing is 80% "does the JSON response match what it should."

2.8 Cookies, sessions, authentication, authorization

  • Cookie: small piece of data the server asks the browser to store and send back on every request (e.g., a session ID).
  • Session: server-side record of "this user is logged in," usually tied to a cookie or token.
  • Authentication: proving who you are (login).
  • Authorization: what you're allowed to do once you're known (roles/permissions).
  • Why QA cares: a huge share of real-world bugs are auth bugs — a regular user seeing admin data, a logged-out user accessing a page they shouldn't, a session that doesn't expire. "Try accessing X without logging in" and "try accessing another user's data by changing the ID in the URL" are two of the most common exploratory testing moves you'll ever make.

2.9 Basic networking & browser basics

You don't need deep networking, but know: DNS resolves a domain name to an IP address; a port identifies a specific service on a server (80 = HTTP, 443 = HTTPS); localhost means your own machine. In the browser, know how to open DevTools (F12) — the Network tab (see actual requests/responses/status codes — this is your best friend for both manual and API-adjacent testing) and the Console tab (see JS errors).

3.3 Shift-left testing Must Know

The principle of moving testing activities as early as possible in the SDLC — reviewing requirements for testability, writing test cases before/during development instead of after, testing each piece as it's built rather than waiting for a "testing phase." This is the dominant modern industry philosophy and interviewers like to hear you understand why: bugs found in requirements cost far less to fix than bugs found in production (commonly cited rule of thumb: cost roughly multiplies at each later stage).

Example: acceptance criteria → test cases

User story

"As a registered user, I want to reset my password via email, so that I can regain access if I forget it."

Acceptance criteria

  • User can request a reset link by entering their registered email.
  • Reset link expires after 30 minutes.
  • Reset link can only be used once.
  • New password must meet the site's password policy.

Notice each bullet is already almost a test case title. This is exactly how professional QAs work — acceptance criteria are the primary input to test design, not an afterthought.

4.1 The phases

4.2 Entry and exit criteria Must Know

  • Entry criteria for test execution: e.g., "build deployed to test environment," "smoke test passed," "test cases reviewed."
  • Exit criteria: e.g., "95% of planned test cases executed," "no open Critical/High severity bugs," "test coverage target met."

Interviewers sometimes ask "when do you stop testing?" — the honest professional answer is never purely by feeling; you define exit criteria up front and check against them, while acknowledging in practice teams also weigh time/budget/risk.

4.3 Worked example: STLC on a real small feature

Feature

"Users can filter a product list by price range on an e-commerce site."

  1. Requirement Analysis: Is "price range" a slider or two input boxes? What happens if min > max? Is there a currency consideration? (You'd raise these as clarifying questions before writing test cases — a hallmark of a good QA engineer is asking sharp clarifying questions, not guessing.)
  2. Test Planning: In scope — filter UI, filter logic, combining filter with other filters (category + price). Out of scope (for this cycle) — performance under 10,000 products.
  3. Test Case Development: e.g., "Verify filtering with min=100, max=500 returns only products in that range (inclusive)"; "Verify min > max shows validation error"; "Verify filter persists after pagination."
  4. Test Environment Setup: Staging site with seeded product data covering edge prices (e.g., a product at exactly 100, one at exactly 500, one at 0, one with no price).
  5. Test Execution: Run cases, log pass/fail, file bugs (e.g., "product priced exactly at max boundary is excluded — off-by-one bug").
  6. Test Closure: 40/42 cases passed, 2 bugs filed (1 High, 1 Low), decision: release with Low bug tracked for next sprint, High bug must be fixed first.

5.1 QA vs. QC vs. Testing

Term Scope Focus
Quality Assurance (QA) Process-oriented, whole project Preventing defects by improving the process itself
Quality Control (QC) Product-oriented Identifying defects in the actual product
Testing A subset of QC The specific activity of executing software to find defects

In real BD job postings, "SQA Engineer" almost always means what is technically QC + Testing work day-to-day, despite the title. Don't get hung up on the terminology mismatch in job titles — but do know the correct definitions cold, because interviewers ask this specific question extremely often as a warm-up.

5.2 Verification vs. Validation Must Master

  • Verification: "Are we building the product right?" — checking against specifications/documents, without executing code (reviews, walkthroughs, inspections).
  • Validation: "Are we building the right product?" — actually executing the software to confirm it meets user needs.

Classic interview one-liner: verification is static, validation is dynamic.

5.3 Error, Defect, Bug, Failure — the causal chain Must Master

flowchart LR
    E[Human Error
mistake by developer/analyst] --> D[Defect / Fault

    D --> F[Failure

  • Error: a human mistake (developer misunderstands a requirement).
  • Defect/Fault/Bug: the flaw that results in the code (these three terms are used near-interchangeably in industry; "bug" is the casual term, "defect" is the formal/Jira term).
  • Failure: the observable incorrect behavior when the defective code actually runs.

A defect can exist without a failure (dead code path never executed). Know this distinction — it's a favorite trick question.

Term Definition

Test scenario A high-level "what to test" — one line, no steps (e.g., "Verify user can log in successfully")

Scenario vs. Test Case — the #1 confused pair. A scenario is what. A test case is how (detailed steps + expected result). One scenario often expands into multiple test cases (positive, negative, boundary variants).

5.6 Functional vs. Non-functional

  • Non-functional: how well does it do it? (performance, security, usability, reliability)

5.8 Positive vs. Negative testing Must Master

  • Positive: valid input, expected to succeed. "Enter a valid email and password → login succeeds."
  • Negative: invalid input, expected to fail gracefully. "Enter no password → see 'password required' error, not a crash."

A shockingly large share of real bugs live in negative testing — junior candidates who only think positive are immediately identifiable as weak.

  • Static: examining artifacts without executing code — requirement reviews, code reviews, walkthroughs.
  • Dynamic: actually running the software.

Test Design Techniques

Must Master
Estimated time: 7 hours

This is the single highest-leverage section for both written tests and interviews — nearly every BD QA written test includes an EP/BVA question.

7.1 Equivalence Partitioning (EP) Must Master

Concept

Divide input data into partitions (groups) where all values in a partition should behave the same way. Instead of testing every possible input, test one representative value per partition — this is the core efficiency argument for EP.

Simple example

A field accepts age 18–60.

  • Partition 1 (invalid): < 18
  • Partition 2 (valid): 18–60
  • Partition 3 (invalid): > 60

Test one value from each: e.g., 10 (invalid), 35 (valid), 75 (invalid) — 3 tests instead of exhaustively testing every age.

Realistic software example

A discount code field that requires alphanumeric, 6-8 characters.

  • Valid partition: alphanumeric, 6-8 chars
  • Invalid: too short (< 6), too long (> 8), contains special characters, empty
Worked example

An e-commerce quantity selector accepts 1–10 items per order. | Partition | Representative value | Expected | |---|---|---| | Invalid (below) | 0 | Rejected | | Valid | 5 | Accepted | | Invalid (above) | 15 | Rejected | | Invalid (type) | "abc" | Rejected |

7.2 Boundary Value Analysis (BVA) Must Master

Concept

Bugs cluster at the edges of partitions, not in the middle — off-by-one errors are the most common defect type in real software. BVA tests the boundary values directly: the minimum, just below minimum, just above minimum, the maximum, just below maximum, just above maximum.

Simple example

Same age field, 18–60. | Test value | Boundary | Expected | |---|---|---| | 17 | just below min | Rejected | | 18 | min | Accepted | | 19 | just above min | Accepted | | 59 | just below max | Accepted | | 60 | max | Accepted | | 61 | just above max | Rejected |

Realistic software example

File upload accepts max 5MB.

  • 4.99MB → accepted, 5.00MB → accepted (boundary itself is usually inclusive — confirm with requirements!), 5.01MB → rejected.
  • Real bug pattern this catches: developers frequently write if size > 5MB (correct) vs if size >= 5MB (off-by-one bug that rejects exactly-5MB files that should be allowed). BVA is the technique for catching this class of bug.

EP + BVA together is how professional QAs actually design test cases for any bounded input — EP gives you the categories, BVA gives you the sharpest values within them.

7.3 Decision Table Testing Must Master

Concept

Used when output depends on a combination of multiple input conditions. Lay out all combinations of conditions as columns, and the resulting action as the last row.

Example

A loan approval system — approve if (Credit Score ≥ 700) AND (Income ≥ ৳30,000). Otherwise reject, unless there's a co-signer, in which case a lower bar applies.

Condition Rule 1 Rule 2 Rule 3 Rule 4
Credit Score ≥ 700 Y Y N N
Income ≥ 30,000 Y N Y N
Has co-signer – Y Y N
Action: Approve ✅ ✅ ✅ ❌

Each column becomes one test case. This technique is exactly what interviewers mean by "how would you test a feature with multiple business rules interacting."

7.4 State Transition Testing Must Know

Concept

Used when the system's behavior depends on its current state and moves to a new state based on an event. Model as states + transitions.

Example

An order's lifecycle — Placed → Confirmed → Shipped → Delivered, with a Cancelled state reachable from Placed or Confirmed but NOT from Shipped.

stateDiagram-v2
    [*] --> Placed
    Placed --> Confirmed
    Placed --> Cancelled
    Confirmed --> Shipped
    Confirmed --> Cancelled
    Shipped --> Delivered
    Shipped --> Cancelled: INVALID (should be blocked)

Good state transition tests specifically include invalid transitions — e.g., "verify a Shipped order cannot be cancelled" is often the highest-value test case, because that's exactly the transition developers forget to guard against.

7.5 Pairwise Testing Should Know

Concept

When multiple independent variables combine (e.g., Browser × OS × Login type), testing every combination explodes exponentially. Pairwise testing selects a much smaller subset that still covers every pair of values at least once — based on the empirical observation that most real bugs are triggered by interactions between just two parameters.

Example

3 browsers × 3 OSes × 2 login types = 18 full combinations, but a pairwise-designed set can cover all pairs in about 9 test cases. (Free tools like PICT can generate these — awareness-level only for you; understanding why it's used is what's tested, not tool proficiency.)

7.6 Cause-Effect Graphing Should Know

A more formal, visual precursor to decision tables — mapping causes (inputs) to effects (outputs) with logical operators (AND/OR/NOT), then converting the graph into a decision table. In practice, most BD interviews just want you to produce the decision table directly; know this term exists and that it's the theoretical basis for decision tables.

7.7 Error Guessing Should Know

Concept

Using experience and intuition to guess where bugs are likely to hide — no formal technique, just informed pattern recognition (empty fields, extremely long strings, special characters, double-clicking a submit button, going back in browser history mid-transaction).

7.8 Checklist-Based Testing Should Know

Using a pre-built checklist of common concerns (e.g., a standard "form validation checklist") to guide testing quickly, especially useful under time pressure.

7.9 Risk-Based Testing Must Know

Concept

Prioritizing testing effort based on the probability a feature will fail combined with the impact if it does. A payment feature (high impact, moderate probability) gets more testing attention than a footer link color (low impact, low probability), even under time pressure.

Low impact High impact
Low probability Test last / skip if no time Test with moderate priority
High probability Test with moderate priority Test first, most thoroughly

8.2 Good vs. bad test case — side by side

❌ Bad:

Title: Test login
Steps: Try to log in
Expected: It should work

✅ Good:

TC_LOGIN_002 — Verify login fails with incorrect password
Preconditions: User account test@example.com exists and is active.
Test Data: Email: test@example.com, Password: WrongPass123
Steps:
1. Navigate to the login page.
2. Enter test@example.com in the Email field.
3. Enter WrongPass123 in the Password field.
4. Click "Login".
Expected Result: Login is rejected. An error message "Incorrect email or password" is displayed. User remains on the login page. No session/token is created.
Priority: High | Severity if fails: Major

The difference: the bad version is unrepeatable and unverifiable — two different testers would do different things and disagree on "did it pass." The good version is precise enough that anyone could execute it identically and get the same verdict.

8.3 A critical, often-missed detail: negative test cases specify the exact expected error

"Should show an error" is weak. "Should show the error message 'Incorrect email or password', not a generic 500 error page, and should NOT reveal whether the email exists" is what a strong QA engineer writes — because that last clause is testing a real security concern (user enumeration).

8.4 Test scenarios → test cases: the systematic thinking process

Before writing any test case, run this checklist mentally for any input field or feature:

  1. Happy path — the simplest valid case.
  2. Negative cases — invalid/missing/malformed input.
  3. Boundary cases — min, max, just outside.
  4. UI/validation — error messages, field states, disabled buttons.
  5. Data integrity — does it save/persist correctly?
  6. Security — can it be bypassed, injected, or abused?
  7. Compatibility — does it behave the same across browsers/devices? (lower priority at entry level, but mention it)
  8. Usability — is the interaction sensible?

This 8-point checklist is your general-purpose "how do I not miss anything" tool — use it below.

8.5 Scenario walkthroughs — from thinking to test cases

Below are 14 objects/features. For each, a short worked example shows the systematic thought process (not just answers) — apply the 8-point checklist above. These deliberately span software UI, physical objects (a favorite BD-interview curveball to test raw testing thinking, decoupled from any tech knowledge), and backend-adjacent features.

1. Login page

  • Happy: valid email + valid password → success, redirected to dashboard.
  • Negative: wrong password; non-existent email; empty fields; SQL-injection-style string in email field (' OR '1'='1); case-sensitivity of email.
  • Boundary: password at min/max allowed length.
  • Security: account lockout after N failed attempts; error message doesn't reveal "email exists but password wrong" vs "email doesn't exist" (prevents user enumeration).
  • Usability: "forgot password" link visible; password field masks input; caps-lock warning.

2. Registration

  • Happy: valid unique email, strong password, all required fields.
  • Negative: duplicate email; weak password rejected per policy; mismatched confirm-password; invalid email format (abc@, abc.com).
  • Boundary: name field at max character limit; age field at policy boundary (e.g., must be 18+).
  • Data integrity: does the account actually get created in the DB with correct field values?
  • Security: password stored hashed, not plaintext (you can't verify this via UI, but you should know to ask/flag it).

3. Password reset

  • Happy: request reset → receive email → click link → set new password → can log in with new password.
  • Negative: request reset for non-existent email (should NOT reveal whether email exists — same message either way); expired link; reused link; link tampered (change token in URL).
  • Boundary: link expiry time — test just before and just after expiry (BVA applied to time!).
  • Security: old password should stop working immediately after reset; other active sessions should ideally be invalidated.

4. OTP (One-Time Password)

  • Happy: correct OTP within time window → verified.
  • Negative: wrong OTP; expired OTP; OTP reused after already being consumed; requesting OTP repeatedly (rate limiting?).
  • Boundary: OTP validity window edges (BVA on time again); max resend attempts.
  • Security: is there a lockout after N wrong attempts to prevent brute-force? Is OTP a predictable pattern (sequential, always same digits)?

5. Search box

  • Happy: valid search term returns relevant results.
  • Negative: empty search; search term with no matches ("no results found" message, not a blank/broken page); special characters; SQL-injection-style input; extremely long input.
  • Boundary: 1-character search; max-length search string.
  • Usability: autocomplete/suggestions behavior; case-insensitivity; whitespace trimming (" laptop " should match "laptop").

6. E-commerce cart

  • Happy: add item → cart count updates → correct price shown.
  • Negative: add out-of-stock item; add item then it goes out of stock while in cart; quantity set to 0 or negative.
  • Boundary: max quantity per item (if limited); max number of distinct items in cart.
  • Data integrity: price shown in cart matches product page price at time of adding — what happens if the price changes while item sits in cart?
  • Concurrency: two tabs open, remove item in one — does the other tab's cart stay consistent or go stale?

7. Checkout / Payment

  • Happy: valid payment method, valid address → order placed, confirmation shown.
  • Negative: expired/invalid card details; insufficient balance; payment gateway timeout; network drops mid-payment.
  • Boundary: order total at any minimum-order-value threshold.
  • Reliability/recovery: what happens if payment succeeds on the gateway side but the response back to the app is lost? (This is a real, high-severity class of bug — "was I charged twice?")
  • Security: no full card number should ever appear in logs or be displayed back.

8. ATM

  • Happy: valid PIN, sufficient balance, valid withdrawal amount → cash dispensed, balance updated, receipt offered.
  • Negative: wrong PIN (3 attempts then card retained — state transition!); insufficient balance; withdrawal amount not a multiple of available note denominations.
  • Boundary: withdrawal at daily limit; exactly at account balance.
  • Recovery: power/network failure after cash is dispensed but before balance is debited — does the bank's system reconcile this correctly? (This is the kind of question that separates strong candidates — thinking about failure mid-transaction.)

9. Elevator

  • Happy: press floor button → elevator arrives, doors open, transports to correct floor.
  • Negative: press button for a floor while already at that floor; press multiple floor buttons in sequence; weight limit exceeded (alarm, doors won't close).
  • Boundary: exactly at max weight/occupancy.
  • Safety/recovery: door obstruction sensor reopens door; power failure — does it stop safely, at nearest floor, with emergency lighting/alarm?
  • Concurrency: two people on different floors both call it simultaneously — correct scheduling logic?

10. Traffic light

  • State transitions: Red → Green → Yellow → Red, verify no invalid transition (e.g., Red directly to Yellow).
  • Timing: correct duration for each state (boundary testing on timing).
  • Edge cases: pedestrian crossing button interaction; power failure fallback behavior (flashing red/off); synchronization with adjacent intersection lights.

11. Calculator

  • Happy: basic operations produce correct results.
  • Negative: divide by zero (should show error, not crash); invalid sequences (pressing operators consecutively, e.g., 5 + + 3).
  • Boundary: very large numbers (overflow behavior); decimal precision limits.
  • Usability: clear/reset button behavior; does it correctly handle order of operations if it's a "smart" calculator?

12. File upload

  • Happy: valid file type/size uploads successfully.
  • Negative: unsupported file type; corrupted file; file with malicious extension disguised (e.g., .exe renamed .jpg); empty file (0 bytes).
  • Boundary: file size at exact max limit (just under, at, just over — BVA again).
  • Security: does the server validate the actual file content/type server-side, not just trust the client-reported extension? Can you upload a script and have it execute?
  • Reliability: upload interrupted mid-transfer — does it fail cleanly or leave a corrupted partial file?

13. Date picker

  • Happy: select a valid date → correctly populates the field.
  • Negative: manually typing an invalid date (Feb 30); selecting a date outside an allowed range (e.g., booking system won't allow past dates).
  • Boundary: first/last day of month; leap year Feb 29; year boundaries (Dec 31 → Jan 1).
  • Usability: does the calendar UI disable invalid dates, or let you pick them and then error?

14. Banking application (fund transfer)

  • Happy: valid recipient, sufficient balance, valid amount → transfer succeeds, both balances update correctly.
  • Negative: transfer to non-existent account; transfer amount exceeding balance; transfer to own account (should this be allowed?); negative or zero amount.
  • Boundary: transfer of exact full balance; daily transfer limit boundary.
  • Data integrity: sender's balance decreases by exactly the transferred amount, receiver's increases by exactly the same — verify via SQL, not just UI, if you have DB access (this is where SQL from Part 12 becomes directly useful in a QA job).
  • Concurrency: two simultaneous transfer requests draining the same account — does the system correctly prevent overdraft (race condition)?
  • Recovery: transaction fails halfway (network drop) — is it fully rolled back, or does money "disappear" from one side without appearing on the other? This is the single most important non-negotiable property of any financial system: atomicity.

What "RCM" means, in one paragraph

Revenue Cycle Management is the whole process of a healthcare provider getting paid: a patient is seen (encounter) → the visit is billed to an insurer as a claim → the payer (insurer) either pays it, partially pays it, or denies it with a reason code → unpaid/denied claims get worked, corrected, and resubmitted. An RCM data analyst's job is almost entirely: query this data to find where money is stuck, where claims are wrong, where denial patterns exist, and how fast (or slow) payers are paying. Every query pattern below maps directly onto that.

12.3 SELECT, WHERE, ORDER BY, LIMIT, DISTINCT Must Master

-- SELECT specific columns
SELECT name, email FROM users WHERE country = 'Bangladesh';

-- every column
SELECT * FROM users;

-- DISTINCT -- unique values only
SELECT DISTINCT country FROM users;

-- ORDER BY -- ASC is default, DESC reverses
SELECT name, created_at FROM users ORDER BY created_at DESC;

-- LIMIT -- cap the number of rows returned
SELECT * FROM users ORDER BY created_at DESC LIMIT 5;
In plain English

SELECT = "show me these columns." FROM = "out of this table." WHERE = "but only rows matching this." ORDER BY = "sorted like this." LIMIT = "only give me this many." Read any query top to bottom in that order and it reads like a sentence.

12.4 Filtering deeper: LIKE, IN, BETWEEN, NULL, AND/OR/NOT Must Master

-- LIKE (pattern matching: % = any characters, _ = exactly one character)
SELECT * FROM users WHERE email LIKE '%@gmail.com';
SELECT * FROM users WHERE name LIKE 'A%';          -- starts with A
SELECT * FROM users WHERE name ILIKE 'a%';         -- Postgres: case-insensitive LIKE

-- IN -- matches any value in a list
SELECT * FROM orders WHERE status IN ('Pending', 'Processing');

-- BETWEEN -- inclusive range
SELECT * FROM orders WHERE amount BETWEEN 500 AND 2000;

-- NULL handling -- this trips up almost everyone at first
SELECT * FROM users WHERE country IS NULL;         -- correct
SELECT * FROM users WHERE country = NULL;           -- WRONG -- always returns zero rows
SELECT * FROM users WHERE country IS NOT NULL;      -- correct "has a value"

-- AND / OR / NOT, and why parentheses matter
SELECT * FROM orders WHERE status = 'Delivered' AND amount > 1000;
SELECT * FROM orders WHERE status = 'Pending' OR status = 'Processing' AND amount > 500;
-- ^ ambiguous to a human reader -- AND binds tighter than OR, so this actually means:
--   status = 'Pending' OR (status = 'Processing' AND amount > 500)
-- Always parenthesize explicitly once you mix AND/OR:
SELECT * FROM orders WHERE (status = 'Pending' OR status = 'Processing') AND amount > 500;
Why = NULL is a trap, explained

NULL means "unknown," not "empty." Any comparison against an unknown value is itself unknown — not true, not false. IS NULL / IS NOT NULL exist specifically because = and != can never detect NULL. This single rule explains a huge share of "why is my WHERE clause silently returning nothing" bugs, in QA and in real analyst work.

12.5 CASE — conditional logic inside a query Must Master

SELECT name,
  CASE
    WHEN country = 'Bangladesh' THEN 'Domestic'
    ELSE 'International'
  END AS region
FROM users;

-- multi-branch CASE, RCM-flavored
SELECT claim_id, billed_amount,
  CASE
    WHEN billed_amount >= 5000 THEN 'High Value'
    WHEN billed_amount >= 1000 THEN 'Standard'
    ELSE 'Low Value'
  END AS claim_tier
FROM claims;

CASE is not a special feature — it's an expression, meaning it can appear anywhere a column can: in SELECT (shown above), inside WHERE, inside an aggregate function (12.9), even inside ORDER BY. That flexibility is exactly why it shows up constantly in both QA scripting and real analyst reporting.

12.6 Data modification: INSERT, UPDATE, DELETE Must Know

INSERT INTO users (id, name, email, country, created_at)
VALUES (101, 'Rafi Ahmed', 'rafi@example.com', 'Bangladesh', '2026-08-01');

UPDATE orders SET status = 'Delivered' WHERE id = 45;

DELETE FROM orders WHERE status = 'Cancelled' AND order_date < '2025-01-01';
The single most important habit in this whole section

Always test UPDATE/DELETE with a SELECT using the exact same WHERE clause first, to see precisely which rows will be affected before you run the destructive version. In a real RCM analyst job, an un-scoped UPDATE claims SET claim_status = 'Paid' with a typo'd or missing WHERE clause is the kind of mistake that shows up in a postmortem. This habit alone prevents that class of incident.

12.7 Aggregate functions & GROUP BY Must Master

SELECT COUNT(*) FROM orders;
SELECT SUM(amount) FROM orders WHERE status = 'Delivered';
SELECT AVG(amount) FROM orders;
SELECT MIN(order_date), MAX(order_date) FROM orders;

-- GROUP BY: one aggregate result per group
SELECT user_id, COUNT(*) AS order_count, SUM(amount) AS total_spent
FROM orders
GROUP BY user_id;

-- RCM version: total billed and claim count per payer
SELECT payer_id, COUNT(*) AS claim_count, SUM(billed_amount) AS total_billed
FROM claims
GROUP BY payer_id;
Rule that trips people up

Every column in the SELECT list that is not wrapped in an aggregate function must appear in the GROUP BY clause. SELECT user_id, product_name, COUNT(*) FROM orders GROUP BY user_id is invalid in Postgres — product_name is neither aggregated nor grouped, so the database doesn't know which row's product_name to show for a group that spans many rows.

12.8 HAVING & complex GROUP BY Must Master

-- HAVING filters AFTER grouping/aggregation -- WHERE can't do this
SELECT user_id, SUM(amount) AS total_spent
FROM orders
GROUP BY user_id
HAVING SUM(amount) > 5000;

-- grouping by more than one column (a "complex" GROUP BY)
SELECT payer_id, claim_status, COUNT(*) AS claim_count
FROM claims
GROUP BY payer_id, claim_status
ORDER BY payer_id, claim_status;

-- HAVING combined with a real business question:
-- which payers have more than 10 denied claims?
SELECT payer_id, COUNT(*) AS denied_count
FROM claims
WHERE claim_status = 'Denied'
GROUP BY payer_id
HAVING COUNT(*) > 10;
Critical distinction (frequently tested)

WHERE filters individual rows before grouping happens. HAVING filters entire groups after aggregation. You cannot write WHERE SUM(amount) > 5000 — at the point WHERE runs, no sum has been computed yet. This is one of the most commonly asked "explain the difference" questions in both QA and analyst interviews.

12.9 Conditional aggregation — the report-building pattern Must Master

In plain English

Putting a CASE expression inside an aggregate function lets you count or sum only the rows that match a condition, instead of running a separate query per condition. It's how you build a single "pivoted" summary row instead of many narrow ones — exactly what a report or dashboard query needs to do.

-- one row per payer, with paid/denied/pending counts side by side
SELECT
  payer_id,
  COUNT(*) AS total_claims,
  COUNT(CASE WHEN claim_status = 'Paid' THEN 1 END) AS paid_count,
  COUNT(CASE WHEN claim_status = 'Denied' THEN 1 END) AS denied_count,
  COUNT(CASE WHEN claim_status = 'Pending' THEN 1 END) AS pending_count,
  SUM(CASE WHEN claim_status = 'Paid' THEN billed_amount ELSE 0 END) AS paid_amount
FROM claims
GROUP BY payer_id;

Compare this to running four separate WHERE claim_status = 'X' GROUP BY payer_id queries and stitching the results together by hand — conditional aggregation does it in one pass, one query, one result set. This exact pattern is one of the most commonly asked "write me a query" questions in data-analyst screens, because it directly tests whether you can build a report, not just filter a table.

12.10 JOINs — INNER, LEFT, RIGHT, multi-table Must Master

From here on we use the RCM schema (12.2).

-- INNER JOIN: only rows with a match in both tables
SELECT c.claim_id, p.full_name, c.billed_amount
FROM claims c
INNER JOIN patients p ON c.patient_id = p.patient_id;

-- LEFT JOIN: all rows from claims, matched payment info if it exists (else NULL)
SELECT c.claim_id, c.billed_amount, cp.paid_amount
FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id;

-- find claims that were never paid at all (classic RCM + QA task)
SELECT c.claim_id, c.billed_amount
FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id
WHERE cp.payment_id IS NULL;

-- RIGHT JOIN: mirror of LEFT JOIN -- rarely used in practice; most people
-- just flip table order and write LEFT JOIN instead, for readability
SELECT c.claim_id, cp.paid_amount
FROM claim_payments cp
RIGHT JOIN claims c ON c.claim_id = cp.claim_id;

-- multi-table join: claim + patient + provider + payer, all at once
SELECT
  c.claim_id, p.full_name AS patient, pr.provider_name,
  py.payer_name, c.billed_amount, c.claim_status
FROM claims c
JOIN patients p  ON c.patient_id  = p.patient_id
JOIN providers pr ON c.provider_id = pr.provider_id
JOIN payers py    ON c.payer_id    = py.payer_id;
Interview-favorite question

"Find all claims that were never paid" is exactly the LEFT JOIN + WHERE ... IS NULL pattern above. Memorize this pattern — it's asked constantly in both QA and analyst interviews because it directly mirrors a real task: finding data-integrity gaps (QA framing) or unpaid revenue (RCM framing). Same query, two job titles.

12.11 Self joins Must Know

-- classic self join: employees and their managers, same table
SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id;

-- RCM-flavored self join: find pairs of claims for the same patient
-- submitted on the same day (possible duplicate submission)
SELECT c1.claim_id AS claim_a, c2.claim_id AS claim_b, c1.patient_id, c1.submitted_date
FROM claims c1
JOIN claims c2
  ON c1.patient_id = c2.patient_id
 AND c1.submitted_date = c2.submitted_date
 AND c1.claim_id < c2.claim_id;   -- avoids matching a row with itself, and avoids duplicate mirror pairs
In plain English

A self join is just joining a table to a second copy of itself so you can compare rows within the same table to each other — "does any other row in this same table relate to this row." The c1.claim_id < c2.claim_id trick is how you stop it from matching a claim to itself, and from returning every pair twice (once each direction).

12.12 Subqueries Must Know

-- subquery in WHERE
SELECT full_name FROM patients
WHERE patient_id IN (SELECT patient_id FROM claims WHERE billed_amount > 5000);

-- subquery in FROM (a "derived table")
SELECT payer_id, AVG(claim_total) AS avg_claim_total
FROM (
  SELECT payer_id, SUM(billed_amount) AS claim_total
  FROM claims
  GROUP BY payer_id, patient_id
) sub
GROUP BY payer_id;

-- scalar subquery in SELECT
SELECT claim_id, billed_amount,
  (SELECT AVG(billed_amount) FROM claims) AS overall_avg
FROM claims;

12.13 Correlated subqueries Must Know

In plain English

A normal subquery runs once, on its own, and hands back a fixed result. A correlated subquery reruns once per row of the outer query, because it references a column from the outer row — think of it as a mini-question asked separately for every single row, instead of one question asked once.

-- for each claim, is its billed_amount above the average for THAT SAME payer?
-- (note: claims.payer_id below refers to the OUTER query's current row --
--  that's what makes this correlated, not a plain subquery)
SELECT c1.claim_id, c1.payer_id, c1.billed_amount
FROM claims c1
WHERE c1.billed_amount > (
  SELECT AVG(c2.billed_amount)
  FROM claims c2
  WHERE c2.payer_id = c1.payer_id
);
Why this matters for an interview

Being able to say out loud "this is correlated because the inner query references the outer query's current row, so conceptually it re-runs per outer row" is a strong signal in a data-analyst screen — it shows you understand why the query works, not just that it happens to return the right answer. It also foreshadows 12.29-12.31 (performance): a correlated subquery over a huge table can be slow precisely because of that per-row re-execution, which is exactly the kind of thing EXPLAIN will show you.

12.14 EXISTS / NOT EXISTS Must Know

-- EXISTS -- often faster than IN for large tables, because it can stop
-- at the first match instead of building a full list to compare against
SELECT p.full_name FROM patients p
WHERE EXISTS (SELECT 1 FROM claims c WHERE c.patient_id = p.patient_id AND c.billed_amount > 5000);

-- NOT EXISTS -- the professional-standard way to write "find missing" queries,
-- often preferred over LEFT JOIN ... IS NULL for readability at scale
SELECT c.claim_id FROM claims c
WHERE NOT EXISTS (SELECT 1 FROM claim_payments cp WHERE cp.claim_id = c.claim_id);

UNION and UNION ALL are worth knowing too: UNION combines two result sets and removes duplicates; UNION ALL combines them and keeps everything, which is also faster, since Postgres skips the duplicate-removal pass.

12.15 CTEs — the WITH clause Must Know

In plain English

A CTE (Common Table Expression) is a named, temporary result set you define at the top of a query with WITH name AS (...), then use later in that same query exactly like a real table. It exists purely to make a complicated query readable — break it into named, logical steps instead of nesting nine subqueries inside each other.

WITH denied_claims AS (
  SELECT claim_id, payer_id, billed_amount
  FROM claims
  WHERE claim_status = 'Denied'
)
SELECT payer_id, COUNT(*) AS denied_count, SUM(billed_amount) AS denied_value
FROM denied_claims
GROUP BY payer_id
ORDER BY denied_value DESC;

payer_paid AS (
  SELECT c.payer_id, SUM(cp.paid_amount) AS total_paid
  FROM claims c
  JOIN claim_payments cp ON c.claim_id = cp.claim_id
  GROUP BY c.payer_id

SELECT
  pt.payer_id,
  pt.total_billed,
  COALESCE(pp.total_paid, 0) AS total_paid,
  pt.total_billed - COALESCE(pp.total_paid, 0) AS outstanding
FROM payer_totals pt
LEFT JOIN payer_paid pp ON pt.payer_id = pp.payer_id
ORDER BY outstanding DESC;

This is a realistic shape for a real RCM report: each CTE computes one clean, named intermediate answer ("total billed per payer," "total paid per payer"), and the final SELECT just combines them. Chaining CTEs like this — instead of one giant nested query — is exactly how a readable analyst query is structured, and it's a strong habit to demonstrate in a take-home or live SQL screen.

12.17 Recursive CTEs — the basics Should Know

In plain English

A recursive CTE is a query that refers to itself, so it can walk through data that has a "repeat this logic on the result of the last step" shape — a chain of dates, an org chart, a category that contains sub-categories. You almost certainly won't be asked to write one from memory at entry level, but recognizing the shape and being able to read one is a real differentiator.

-- generate a series of dates (useful for building a complete aging report
-- that doesn't silently skip days with zero claims)
WITH RECURSIVE date_series AS (
  SELECT DATE '2026-01-01' AS d
  UNION ALL
  SELECT d + 1 FROM date_series WHERE d + 1 <= DATE '2026-01-31'
)
SELECT d FROM date_series;

-- (in real Postgres work you'd usually reach for generate_series() instead --
--  generate_series(DATE '2026-01-01', DATE '2026-01-31', INTERVAL '1 day') --
--  but understanding the recursive-CTE version is what explains WHY that
--  built-in function exists and what it's doing under the hood)

Structurally every recursive CTE has the same two halves: an anchor (the starting row(s), before UNION ALL) and a recursive term (the part after UNION ALL that refers back to the CTE's own name) that keeps running until it produces no more new rows.

12.18 Window functions — the concept Must Master

In plain English

GROUP BY collapses many rows into one row per group — you lose the individual rows. A window function calculates something across a group of related rows (a "window") but keeps every original row visible. That's the entire idea: aggregate-like power, without collapsing the detail.

-- every window function follows this shape:
--   FUNCTION() OVER (PARTITION BY ... ORDER BY ...)
-- PARTITION BY = "reset/group by this" (like GROUP BY, but doesn't collapse rows)
-- ORDER BY inside OVER() = the order the window function should process rows in

SELECT
  claim_id, payer_id, billed_amount,
  AVG(billed_amount) OVER (PARTITION BY payer_id) AS payer_avg_amount
FROM claims;
-- every claim row still shows individually, but now also shows its payer's average
-- alongside it -- impossible with plain GROUP BY without a self-join
This is the single highest-leverage new topic in this section

Window functions are what separates "can write basic reporting SQL" from "can write real analyst SQL." RCM-style questions like "rank each patient's claims by amount," "show each claim next to the payer's running total," or "find the days between a claim and that same patient's previous claim" are all window-function questions. Expect them in a Commure/Augmedix-style screen.

12.19 ROW_NUMBER, RANK, DENSE_RANK Must Master

SELECT
  claim_id, payer_id, billed_amount,
  ROW_NUMBER() OVER (PARTITION BY payer_id ORDER BY billed_amount DESC) AS rn,
  RANK()       OVER (PARTITION BY payer_id ORDER BY billed_amount DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY payer_id ORDER BY billed_amount DESC) AS drnk
FROM claims;

-- classic use: the single highest-billed claim per payer
WITH ranked AS (
  SELECT claim_id, payer_id, billed_amount,
    ROW_NUMBER() OVER (PARTITION BY payer_id ORDER BY billed_amount DESC) AS rn
  FROM claims
)
SELECT * FROM ranked WHERE rn = 1;
FunctionTies (same value)Gaps after a tie
ROW_NUMBER()Breaks ties arbitrarily — always gives 1,2,3,4...No gaps, ever
RANK()Tied rows get the same rankSkips the next rank(s) — e.g. 1,2,2,4
DENSE_RANK()Tied rows get the same rankNo gap — e.g. 1,2,2,3
Interview trap

"What's the difference between RANK and DENSE_RANK" is asked constantly precisely because the table above is easy to memorize but easy to blank on live. The trick to never forgetting it: RANK "leaves a gap the size of the tie," DENSE_RANK never leaves gaps. ROW_NUMBER never even looks at ties — it just numbers 1..n regardless.

12.20 LAG / LEAD Must Know

-- for each claim, show the previous claim's submitted_date for that same patient
SELECT
  claim_id, patient_id, submitted_date,
  LAG(submitted_date) OVER (PARTITION BY patient_id ORDER BY submitted_date) AS prev_submitted_date,
  submitted_date - LAG(submitted_date) OVER (PARTITION BY patient_id ORDER BY submitted_date) AS days_since_last_claim
FROM claims;

-- LEAD works identically but looks FORWARD instead of backward
SELECT
  claim_id, patient_id, submitted_date,
  LEAD(submitted_date) OVER (PARTITION BY patient_id ORDER BY submitted_date) AS next_submitted_date
FROM claims;
In plain English

LAG = "what was the value in the previous row (within this patient's group)?" LEAD = "what's the value in the next row?" It's how you compare a row to its neighbor without a self-join — genuinely one of the most useful patterns for anything involving a sequence of events over time, which is most of what RCM data is.

12.21 Running totals & moving aggregates Should Know

-- running (cumulative) total of payments received, ordered by date
SELECT
  payment_date, paid_amount,
  SUM(paid_amount) OVER (ORDER BY payment_date) AS running_total
FROM claim_payments
ORDER BY payment_date;

-- 7-row moving average (frame clause -- advanced but good to recognize)
SELECT
  payment_date, paid_amount,
  AVG(paid_amount) OVER (
    ORDER BY payment_date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS moving_avg_7
FROM claim_payments
ORDER BY payment_date;

This is exactly the query shape behind "collections trend over time" or "revenue running total" charts — a dashboard's line chart is almost always a window function like this, one row per data point, running underneath it.

12.22 Date & time analysis Must Master

-- date arithmetic
SELECT claim_id, submitted_date, submitted_date + 30 AS due_in_30_days FROM claims;

-- difference between two dates (Postgres returns an integer number of days)
SELECT claim_id, service_date, submitted_date, submitted_date - service_date AS days_to_submit
FROM claims;

-- EXTRACT -- pull out a part of a date
SELECT claim_id, EXTRACT(YEAR FROM submitted_date) AS yr, EXTRACT(MONTH FROM submitted_date) AS mo
FROM claims;

-- DATE_TRUNC -- round a date DOWN to a unit -- the standard way to group by month/week
SELECT DATE_TRUNC('month', submitted_date) AS claim_month, COUNT(*) AS claim_count, SUM(billed_amount) AS total_billed
FROM claims
GROUP BY DATE_TRUNC('month', submitted_date)
ORDER BY claim_month;

-- the single most important RCM date query: days-to-payment, and aging buckets
SELECT
  c.claim_id,
  c.submitted_date,
  cp.payment_date,
  cp.payment_date - c.submitted_date AS days_to_payment,
  CASE
    WHEN cp.payment_id IS NULL AND CURRENT_DATE - c.submitted_date <= 30 THEN '0-30 days'
    WHEN cp.payment_id IS NULL AND CURRENT_DATE - c.submitted_date <= 60 THEN '31-60 days'
    WHEN cp.payment_id IS NULL AND CURRENT_DATE - c.submitted_date <= 90 THEN '61-90 days'
    WHEN cp.payment_id IS NULL THEN '90+ days'
    ELSE 'Paid'
  END AS aging_bucket
FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id;
Why aging buckets matter so much in RCM

"Accounts Receivable aging" (how long unpaid claims have been sitting, bucketed into ranges like 0-30/31-60/61-90/90+ days) is one of the single most common reports in any RCM role, because the older an unpaid claim gets, the less likely it is to ever be collected. Being able to build this query from scratch — CASE + date arithmetic + a LEFT JOIN for "unpaid" — is close to a guaranteed interview or take-home question for this exact role.

12.24 NULL handling, deeper Must Know

-- COALESCE -- return the first non-NULL value in a list; the standard way
-- to supply a default instead of a NULL
SELECT claim_id, COALESCE(cp.paid_amount, 0) AS paid_amount
FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id;

-- NULLIF -- return NULL if two values are equal (useful to avoid divide-by-zero)
SELECT payer_id, total_billed / NULLIF(claim_count, 0) AS avg_claim_value
FROM (SELECT payer_id, SUM(billed_amount) AS total_billed, COUNT(*) AS claim_count FROM claims GROUP BY payer_id) t;

-- IS DISTINCT FROM -- a NULL-safe equality check (treats NULL = NULL as true)
SELECT * FROM claims WHERE claim_status IS DISTINCT FROM 'Paid';
In plain English

COALESCE(x, 0) means "use x, but if x is missing, use 0 instead." It's the single most-used NULL-handling function in real reporting SQL, because unmatched LEFT JOINs produce NULLs constantly (12.10) and you almost always want a clean default (0, 'Unknown', etc.) instead of a blank in your final report.

12.25 Duplicate detection, data cleaning & data validation Must Master

-- duplicate detection pattern -- memorize this, asked constantly
SELECT patient_id, service_date, provider_id, COUNT(*) AS cnt
FROM claims
GROUP BY patient_id, service_date, provider_id
HAVING COUNT(*) > 1;
-- reads as: "same patient, same day, same provider, more than once" --
-- a strong signal of an accidental duplicate claim submission

-- data validation: are billed_amount values ever impossible (negative, zero, absurd)?
SELECT * FROM claims WHERE billed_amount <= 0 OR billed_amount > 100000;

-- data validation: does every claim reference a patient/provider/payer that actually exists?
-- (referential-integrity check -- should return zero rows in a healthy database)
SELECT c.claim_id FROM claims c
LEFT JOIN patients p ON c.patient_id = p.patient_id
WHERE p.patient_id IS NULL;

-- data cleaning: normalize inconsistent status text before analysis
SELECT claim_id, INITCAP(TRIM(claim_status)) AS clean_status FROM claims;

12.26 Reconciliation queries Must Master

In plain English

Reconciliation just means "do two numbers that are supposed to match, actually match?" In RCM: does the sum of what was billed equal the sum of what was recorded as paid plus what's still outstanding? If not, money is unaccounted for — and finding exactly which claims caused the mismatch is the actual job.

-- does billed_amount reconcile against the sum of its payments?
SELECT
  c.claim_id,
  c.billed_amount,
  COALESCE(SUM(cp.paid_amount), 0) AS total_paid,
  c.billed_amount - COALESCE(SUM(cp.paid_amount), 0) AS variance
FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id
GROUP BY c.claim_id, c.billed_amount
HAVING c.billed_amount - COALESCE(SUM(cp.paid_amount), 0) <> 0;

-- find "orphaned" payments -- a payment referencing a claim_id that
-- doesn't exist in claims at all (a real, damaging data-integrity bug)
SELECT cp.* FROM claim_payments cp
LEFT JOIN claims c ON cp.claim_id = c.claim_id
WHERE c.claim_id IS NULL;

-- claims marked 'Paid' that actually have NO payment row -- a status/data mismatch
SELECT c.claim_id FROM claims c
LEFT JOIN claim_payments cp ON c.claim_id = cp.claim_id
WHERE c.claim_status = 'Paid' AND cp.payment_id IS NULL;

12.27 Finding anomalies Should Know

-- claims billed far above the norm for their payer (simple outlier check)
WITH payer_stats AS (
  SELECT payer_id, AVG(billed_amount) AS avg_amt, STDDEV(billed_amount) AS stddev_amt
  FROM claims
  GROUP BY payer_id
)
SELECT c.claim_id, c.payer_id, c.billed_amount, ps.avg_amt
FROM claims c
JOIN payer_stats ps ON c.payer_id = ps.payer_id
WHERE c.billed_amount > ps.avg_amt + 3 * ps.stddev_amt;   -- more than 3 standard deviations out

-- a payer whose denial rate suddenly looks wrong this month vs. last month
-- (this is exactly a LAG comparison -- 12.20 -- applied to a monthly aggregate)
WITH monthly_denials AS (
  SELECT payer_id, DATE_TRUNC('month', denial_date) AS mo, COUNT(*) AS denied_count
  FROM denials d JOIN claims c ON d.claim_id = c.claim_id
  GROUP BY payer_id, DATE_TRUNC('month', denial_date)
)
SELECT payer_id, mo, denied_count,
  LAG(denied_count) OVER (PARTITION BY payer_id ORDER BY mo) AS prev_month_count
FROM monthly_denials;

You don't need to be a statistician for this role. "More than N standard deviations from the mean" and "compare this period to the previous period with LAG" cover the large majority of anomaly-detection questions an entry-level RCM analyst is realistically asked to build.

12.28 Complex business logic — putting it all together Must Master

A real analyst deliverable rarely uses just one technique — it chains several. Here's a full "denial rate and revenue impact by payer" report, combining a CTE, conditional aggregation, and a window function in one query:

WITH claim_summary AS (
  SELECT
    c.payer_id,
    py.payer_name,
    COUNT(*) AS total_claims,
    COUNT(CASE WHEN c.claim_status = 'Denied' THEN 1 END) AS denied_claims,
    SUM(CASE WHEN c.claim_status = 'Denied' THEN c.billed_amount ELSE 0 END) AS denied_revenue,
    SUM(c.billed_amount) AS total_billed
  FROM claims c
  JOIN payers py ON c.payer_id = py.payer_id
  GROUP BY c.payer_id, py.payer_name
)
SELECT
  payer_name,
  total_claims,
  denied_claims,
  ROUND(100.0 * denied_claims / NULLIF(total_claims, 0), 1) AS denial_rate_pct,
  denied_revenue,
  RANK() OVER (ORDER BY denied_revenue DESC) AS revenue_impact_rank
FROM claim_summary
ORDER BY revenue_impact_rank;

Notice the shape: a CTE builds one clean per-payer summary; the outer query turns that into percentages and a rank. This "CTE that summarizes, then an outer query that presents" pattern is worth internalizing — it's how the overwhelming majority of real analyst SQL is actually structured, and it's a strong signal to write it this way (instead of one giant nested query) in any live SQL exercise.

12.29 Indexes Should Know

In plain English

An index is like the index at the back of a textbook — instead of reading every page to find a topic, you jump straight to the right page. Without an index on a column, the database has to scan every single row to find matches on that column; with one, it can jump almost straight there.

CREATE INDEX idx_claims_patient_id ON claims(patient_id);
CREATE INDEX idx_claims_payer_status ON claims(payer_id, claim_status);  -- composite index
Good candidate for an indexUsually not worth indexing
Columns used constantly in WHERE/JOIN (e.g. patient_id, foreign keys)Columns almost never filtered/joined on
Columns used in ORDER BY on large result setsSmall tables (a full scan is already fast)
High-cardinality columns (many distinct values)Low-cardinality columns (e.g. a boolean flag) — an index barely helps

The tradeoff: indexes speed up reads but slow down writes slightly (every INSERT/UPDATE also has to update the index), and they take disk space. As an analyst you'll rarely be the one deciding what to index, but you're expected to recognize why a query is slow and be able to say "this needs an index on X" when asked.

12.30 EXPLAIN & reading query plans Should Know

EXPLAIN ANALYZE
SELECT c.claim_id, p.full_name
FROM claims c
JOIN patients p ON c.patient_id = p.patient_id
WHERE c.claim_status = 'Denied';
What to actually look for

You don't need to master every line of a query plan. Look for: Seq Scan (sequential scan — reading every row; fine on a small table, a red flag on a huge one if there's a WHERE/JOIN column that could be indexed instead) vs. Index Scan (using an index — the thing you generally want on large tables); the estimated vs. actual row counts (a huge mismatch means the database's statistics are stale, which can cause it to pick a bad plan); and the total execution time at the bottom. Being able to say "I ran EXPLAIN ANALYZE and saw a sequential scan on a 2-million-row table, which is why this took 8 seconds" is exactly the kind of answer that separates a candidate who's only ever written correct SQL from one who's also written fast SQL.

12.31 N+1 thinking & writing efficient queries against large datasets Should Know

In plain English

The "N+1 problem" is running one query to get a list, then a separate query per row of that list to get related data — 1 query becomes 1 + N queries. It's usually an application/ORM mistake (fetch 500 claims, then loop and run a separate "get payments for this claim" query 500 times) rather than something you'd write by hand in raw SQL, but recognizing it is valuable because the fix is almost always "do it in one JOIN or one window function instead" — exactly the tools from this whole section.

  • Select only the columns you need — avoid SELECT * in real reporting queries; it pulls unnecessary data across the network and can prevent certain index-only optimizations.
  • Avoid wrapping an indexed column in a function inside WHERE — WHERE DATE(submitted_date) = '2026-01-01' can prevent the database from using an index on submitted_date; WHERE submitted_date >= '2026-01-01' AND submitted_date < '2026-01-02' usually can.
  • Filter as early as possible — apply WHERE conditions before joining large tables together where the logic allows it, so the database has less data to join.
  • Prefer EXISTS over IN with a large subquery — EXISTS can stop at the first match (12.14); a large IN list has to be fully materialized first.
  • Use LIMIT while developing a query against a huge table, so you're not waiting on a full result set every time you tweak a WHERE clause.

15.1 Why test the API directly instead of only the UI

APIs are faster to test (no UI rendering), more stable (UI changes don't break your tests), and let you test backend logic and edge cases the UI might not even expose (e.g., sending malformed data the UI form would normally prevent you from typing). API testing is also how you verify the backend is correct independent of whether the frontend correctly displays it — isolating where a bug actually lives.

15.2 REST fundamentals (recap + depth)

REST APIs organize functionality around resources (nouns, e.g. /users, /orders) and use HTTP methods (verbs) to say what to do:

Method Purpose Idempotent? Example
GET Retrieve data Yes GET /users/5
POST Create new data No POST /users
PUT Replace an entire resource Yes PUT /users/5
PATCH Partially update a resource No (generally) PATCH /users/5
DELETE Remove a resource Yes DELETE /users/5

Idempotent means calling it multiple times has the same effect as calling it once (GET-ing the same resource repeatedly doesn't change anything; PUT-ing the exact same full replacement repeatedly leaves the same end state). POST is NOT idempotent — calling it twice typically creates two resources. This idempotency distinction is a real interview question at API-testing-aware companies.

Headers Metadata about the request Content-Type: application/json, Authorization: Bearer <token>

Path parameters Part of the URL path identifying a specific resource GET /orders/{id} → /orders/42
Request body The actual data being sent (POST/PUT/PATCH) {"name": "Rafi", "email": "rafi@x.com"}

15.4 What "response validation" actually means

A full API test checks, at minimum:

  1. Status code — is it the correct one for this scenario?
  2. Response body structure — correct fields present, correct data types (schema validation).
  3. Response body values — correct actual data.
  4. Response headers — e.g., Content-Type: application/json present and correct.
  5. Response time — reasonable (basic performance awareness, not full load testing).

15.6 Authentication in APIs Must Know

Most real APIs require auth on protected endpoints — commonly a Bearer token in the Authorization header (Authorization: Bearer <token>), obtained via a login/token endpoint first. Test both: valid token works, and — importantly — an expired/invalid/missing token is correctly rejected (401), and a valid token for User A cannot access User B's private data (403 or 404 depending on design — this is an authorization check, not authentication, and it's one of the most commonly missed real-world bug classes).

Automation Testing: Playwright

Must Know
Estimated time: 18 hours

With the extra room, hands-on automation is worth doing for real, not just conceptually. It stays 🟠 MUST KNOW, not 🔴 MUST MASTER: most BD entry-level manual/API QA roles still don't require it day one, but walking into an interview with a real, working automation suite on your GitHub is one of the sharpest differentiators available to a fresher.

A.1 Why Playwright, and why only one tool

Two automation tools done shallowly is weaker than one done properly — trying to hand-roll both Selenium and Playwright inside a tight budget was producing surface-level knowledge of each instead of a real, working suite of either. Playwright is the better single choice for this: it auto-waits for elements by default (removing the single biggest source of flaky, hard-to-debug tests), installs its own managed browsers so setup rarely breaks, and ships a built-in trace viewer and codegen recorder that make debugging dramatically easier for someone building their first suite. It's also the direction a growing share of newer BD teams and greenfield projects are adopting, so it reads as current, not dated.

In plain English

Automation doesn't replace manual testing — it replaces the boring, repetitive parts of manual testing (regression) so a human tester has time for the parts that actually need judgment (exploratory, usability). Playwright is just the tool that drives a real browser — clicking, typing, reading the page — the way a script instead of a human.

A.2 How Playwright actually works

Concept

Playwright launches and controls a real browser (Chromium, Firefox, or WebKit) over a fast, persistent connection, and drives it exactly the way a human would — clicking, typing, reading the rendered page. It does not talk to your app's backend directly; it only sees what the browser sees, which is precisely why it's valuable for QA: it tests the same path a real user takes.

from playwright.sync_api import sync_playwright, expect

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    page.goto("https://example.com/login")

    page.get_by_label("Email").fill("qa.test@example.com")
    page.get_by_label("Password").fill("Pass1234")
    page.get_by_role("button", name="Login").click()

    # Playwright auto-waits for this element before asserting -- no manual wait needed
    expect(page.get_by_role("heading", name="Dashboard")).to_be_visible()

    browser.close()

A.3 Locators, ranked by how stable they are Must Master

Locator Example Stability
get_by_role page.get_by_role("button", name="Login") Best — mirrors how a real user/screen-reader identifies the element, survives most styling/markup changes
get_by_label page.get_by_label("Email") Excellent for form fields — matches the associated <label>
get_by_test_id page.get_by_test_id("submit-btn") Best when available — a data-testid attribute added specifically for tests, immune to styling/copy changes
get_by_text page.get_by_text("Forgot password?") Good for static, unique visible text
CSS selector page.locator(".btn-primary") Fine as a fallback when nothing above fits; more brittle to styling changes
Interview trap

A candidate who reaches for a raw CSS selector or XPath first, for everything, reads as inexperienced. The correct instinct with Playwright is get_by_role/get_by_label/get_by_test_id first — they're both more stable and more readable — with CSS only as a fallback when nothing semantic is available.

A.4 Auto-waiting — why you almost never write a manual wait

  • Old-style time.sleep(3): never do this. It's either too short (flaky failures) or wastes time (too long on every run, and at scale this compounds into hours of wasted CI time).
  • Playwright's default behavior: every action (.click(), .fill()) and every expect(...) assertion automatically retries until the element is actionable/visible or a timeout is hit. This single behavior removes the majority of "flaky test" bugs that plague junior-written Selenium suites — it's the main practical reason this module teaches only Playwright.
# no manual wait needed anywhere here -- Playwright retries internally
page.get_by_role("button", name="Submit").click()
expect(page.get_by_text("Saved successfully")).to_be_visible()

A.5 Page Object Model (POM) Must Know

Concept

Instead of scattering locators and interactions across every test, encapsulate one page's elements and actions inside a class. When the UI changes, you fix it in exactly one place instead of every test that touches that page.

# pages/login_page.py
class LoginPage:
    def __init__(self, page):
        self.page = page
        self.email = page.get_by_label("Email")
        self.password = page.get_by_label("Password")
        self.submit = page.get_by_role("button", name="Login")

    def login(self, email, password):
        self.page.goto("https://example.com/login")
        self.email.fill(email)
        self.password.fill(password)
        self.submit.click()

# tests/test_login.py
from pages.login_page import LoginPage
from playwright.sync_api import expect

def test_valid_login(page):
    login = LoginPage(page)
    login.login("qa.test@example.com", "Pass1234")
    expect(page.get_by_role("heading", name="Dashboard")).to_be_visible()

def test_invalid_password(page):
    login = LoginPage(page)
    login.login("qa.test@example.com", "WrongPass")
    expect(page.get_by_text("Incorrect email or password")).to_be_visible()

B.1 Why a QA engineer needs any of this

B.2 Processes vs. threads Must Master

Process Thread
Definition An independent running program with its own memory space A unit of execution within a process, sharing that process's memory
Isolation Fully isolated from other processes (a crash in one usually doesn't crash another) Threads in the same process share memory — a bug in one can corrupt shared state used by another
Communication Needs explicit inter-process communication (sockets, pipes, shared files) Can directly share variables/data (which is also why threading bugs are harder to find)
Cost Heavier to create/switch between Lighter — cheaper to create, faster to switch between
Classic interview one-liner

a process is an isolated program; a thread is a lightweight worker inside that program, sharing its memory.

B.3 Memory basics Must Know

  • Stack: memory for function calls and local variables — fast, automatically freed when a function returns, limited in size (a runaway recursive function causes a stack overflow, the actual technical meaning behind the website's name).
  • Heap: memory for data that needs to outlive a single function call (objects, dynamically-sized structures) — must be explicitly managed or garbage-collected; a program that keeps allocating heap memory without releasing it has a memory leak, which is exactly why long-running services (and long-running automated test suites!) can slowly consume more and more RAM until they crash or slow to a crawl.
  • Virtual memory: each process believes it has its own full, private address space; the OS maps this onto physical RAM (and disk, via swapping) behind the scenes. This is why one process running out of memory doesn't directly corrupt another process's memory.
In plain English

A memory leak in a long-running test automation suite (Part A) is a real, common failure mode — if your CI suite gets progressively slower over hundreds of runs, memory (not just test logic) is a reasonable first suspect.

B.4 Deadlocks and race conditions Must Know

  • Race condition: the outcome depends on the unpredictable timing/order of two or more operations happening close together — exactly the bug class behind the "two simultaneous transfer requests draining the same account" scenario from Part 8.5's banking example. This is a real, testable QA concern, not just theory: concurrency test cases exist specifically to try to trigger these.
  • Deadlock: two (or more) processes/threads each hold a resource the other needs, and neither can proceed — everything freezes. The textbook analogy: two people trying to pass each other in a narrow hallway, each waiting for the other to move first.

B.5 CPU scheduling and OS basics — awareness level Awareness

The OS scheduler decides which process/thread gets CPU time next, using strategies like round-robin (each process gets a small time slice in turn) or priority-based scheduling. Awareness only at your level: know these terms exist and roughly what they mean if a written test asks a definitional question; you will not be asked to design a scheduler.

B.7 TCP vs. UDP Must Master

TCP UDP

B.8 The TCP three-way handshake — concept only Awareness

Before any TCP data flows, the client and server exchange three messages to establish a connection: SYN (client: "let's connect") → SYN-ACK (server: "okay, let's connect") → ACK (client: "confirmed"). Awareness level: know it exists and why (it's how TCP establishes a reliable connection before trusting any data) — you won't be asked to diagram packet flags.

B.9 DNS — how a domain name becomes a server Must Know

DNS (Domain Name System) translates a human-readable domain into the IP address a computer actually connects to — already mentioned briefly in Part 2.9, expanded here because "explain what happens when you type a URL and press Enter" is one of the most common general-technical interview questions across both QA and dev roles, and DNS resolution is always expected as part of a complete answer.

B.10 Ports — why localhost:8000 and localhost:5432 don't collide Must Know

A port is a number that identifies a specific service on a machine, letting one IP address run many independent network services simultaneously. Common ones worth recognizing cold: 80 (HTTP), 443 (HTTPS), 22 (SSH), 3306 (MySQL), 5432 (PostgreSQL), 5173/3000/8000 (common local dev-server defaults). When your test environment URL is staging.example.com:8080, the :8080 is telling your browser which service on that server to talk to.

B.11 "What happens when you type a URL and press Enter?" — the model answer Must Master

This exact question (or a close variant) appears often enough across BD tech interviews — QA and dev alike — that it's worth having a clean, complete answer memorized:

  1. The browser checks if it already knows the IP for that domain (cache); if not, it asks a DNS resolver to look it up.
  2. The browser opens a TCP connection to that IP on the right port (443 for HTTPS).
  3. For HTTPS, a TLS handshake happens — client and server agree on encryption and verify the server's certificate, so the connection is encrypted from this point on.
  4. The browser sends an HTTP request (method, path, headers) over that encrypted connection.
  5. The server processes the request (runs backend logic, queries a database) and sends back an HTTP response (status code, headers, body).
  6. The browser parses and renders the response (HTML/CSS/JS, or in an API context, hands the JSON back to whatever called it).

Every single piece of this sentence maps to something you've already studied in this guide (Parts 2, 12, 15) or in B.6-B.9 above — this question is really just asking you to assemble the pieces into one coherent story.

B.12 TLS/HTTPS — what "encrypted" actually buys you Must Know

HTTPS is HTTP sent over a TLS-encrypted connection. Practically, for testing purposes, this means: data in transit can't be read or tampered with by anyone intercepting the network traffic between client and server (a public Wi-Fi network, for instance). It does not mean the data is encrypted once it reaches the server's database — that's a separate concern (encryption at rest), and conflating the two is a common junior mistake worth avoiding out loud in an interview.

B.13 File systems & permissions — the Linux tie-in Should Know

19.1 Selenium & Browser Automation (concept only)

What it is

Selenium WebDriver is a tool that programmatically controls a real browser — clicking, typing, reading page content — so test scripts can replay UI interactions automatically instead of a human doing it by hand.

Core concepts to recognize by name (not implement):

Term Meaning
WebDriver The component that talks to and controls the browser
Locators Ways to find an element on a page: id, name, class, CSS selector, XPath
XPath A query language for navigating HTML/XML structure, e.g. //button[@id='submit']
Explicit wait Waiting for a specific condition (e.g., element becomes clickable) before proceeding — prevents flaky tests
Implicit wait A global timeout applied to all element lookups
Page Object Model (POM) A design pattern where each page of the app has a corresponding class encapsulating its elements/actions, keeping test code maintainable
Why POM matters conceptually

if the login button's HTML changes, without POM you'd have to fix that locator in every test file that clicks it; with POM, you fix it in one place (the LoginPage class). This design principle — separating "what a page can do" from "what a test asserts" — is worth understanding even without writing the code, because it's a genuinely good software engineering habit that also applies to Django's separation of concerns later.

Interview-safe things to say if asked

"I've built a real, working automation suite with Playwright — including Page Object Model structure, auto-waiting, and a CI pipeline — and I understand Selenium's core concepts (locators, explicit/implicit waits, POM) even though my hands-on depth is specifically in Playwright. The underlying approach transfers directly if a role needs Selenium specifically."

19.3 Security Testing Basics (recognize, don't exploit)

A junior QA is expected to recognize these risk categories during normal functional testing, not perform formal penetration testing.

Concept What a QA should recognize
SQL Injection Malicious SQL smuggled through an input field (e.g., ' OR '1'='1) that could manipulate a database query if the backend doesn't properly sanitize/parameterize input
XSS (Cross-Site Scripting) Malicious script (e.g., <script>alert(1)</script>) submitted through an input and later rendered/executed in another user's browser
CSRF (Cross-Site Request Forgery) Tricking a logged-in user's browser into making an unwanted request to a site they're authenticated on
Password security Passwords should never be visible in plaintext (in DB, logs, or network traffic over HTTP); should be hashed
Session management Sessions should expire, logout should actually invalidate the session (not just hide the UI), tokens shouldn't be guessable
Access control (authZ) A regular user should never be able to reach admin-only data/actions by directly manipulating a URL or API call
File upload security Uploaded files should be validated server-side, not just by client-reported extension
Input validation Every user input should be validated/sanitized server-side, never trusted from the client alone
The one practical technique worth actually trying

type ' OR '1'='1 or <script>alert(1)</script> into a normal text input during your own manual testing, and observe what happens. This costs nothing, requires no tooling, and is a real (if basic) security-awareness move that shows up favorably in interviews when you mention you do it as a habit.

19.4 CI/CD Fundamentals (concept only)

flowchart LR
    A[Code Commit] --> B[CI: Build]
    B --> C[CI: Run Automated Tests]
    C -->|Pass| D[CD: Deploy to Staging]
    C -->|Fail| E[Notify Team, Block Merge]

  • CI (Continuous Integration): automatically building and testing code every time it's committed, catching integration issues early.
  • CD (Continuous Deployment/Delivery): automatically (or semi-automatically) releasing code that passes CI to staging/production.
  • GitHub Actions / Jenkins: common tools that run these pipelines. Know they exist and roughly what a pipeline config file does (triggers on a git event, runs a sequence of steps) — not hands-on pipeline authorship at this stage.
  • Why QA cares: in a CI/CD world, automated tests (if they exist) run on every commit automatically, and manual/exploratory QA typically happens on the resulting staging deployment, not on developers' laptops. Agile QA & Professional Communication

Must Know
Estimated time: 4 hours

20.1 QA's actual day-to-day inside a Scrum team

A realistic sprint, from a QA's chair:

  1. Sprint planning: you review upcoming stories for testability, flag ambiguous acceptance criteria.
  2. During the sprint: as devs finish pieces, you write test cases from acceptance criteria, execute them as builds become available, log bugs, retest fixes.
  3. Regression: near sprint end, you re-run a regression suite (manual checklist or automated, if it exists) to make sure nothing else broke.
  4. Bug triage: meeting (formal or informal) where the team collectively decides bug priority — is this fixed this sprint, or backlogged?
  5. Sprint review: you may demo tested functionality or confirm what's genuinely "done."
  6. Retrospective: you raise process issues (e.g., "we keep getting builds too late in the sprint to test properly").

20.2 Communicating with different roles

Audience What they care about How to adjust your communication
Developers Exact technical reproduction steps, logs, root cause hints Be precise, technical, non-judgmental — "I found X" not "you broke X"
Product Managers Business impact, user experience risk Lead with impact ("this blocks checkout for X% of users"), not technical detail
Business Analysts Whether behavior matches requirements/acceptance criteria Reference the specific acceptance criterion that's violated
QA Lead Test coverage, risk areas, blockers Be honest about what's NOT tested yet, not just what passed
Customers (rare, but possible) Confidence the product works, plain language No jargon, focus on outcomes not internals

20.3 Scenario-based professional judgment Must Master

"How do you disagree professionally with a developer who says a bug isn't a bug?" Model answer approach: restate the acceptance criteria or expected behavior objectively, provide clear reproduction evidence, ask clarifying questions rather than asserting ("Can you help me understand the intended behavior here? Based on the acceptance criteria, I expected X but observed Y.") — avoid framing it as a personal disagreement; frame it as a shared question about what's correct.

"How do you report a critical bug found right before release?" Escalate immediately and directly (don't wait for the next standup) to whoever owns the release decision, with clear severity/impact framing, and let them make the release-vs-delay call — it's not solely your call, but it is your job to surface it loudly and immediately.

"What do you do when a developer says 'works on my machine'?" Provide exact environment details (browser/OS/build version), ask what their environment differs by, and offer to pair/screen-share to reproduce live — this phrase almost always means an environment or data difference, not that you're wrong.

"What do you do when requirements conflict or are ambiguous?" Don't guess and don't silently pick one interpretation — flag it explicitly to the PM/BA/team, ideally before you've built test cases around a wrong assumption, and document the clarification once you get it (in the ticket, not just verbally) so it doesn't get re-litigated later.

"How do you prioritize testing when time is limited?" Apply risk-based testing (Part 7.9) explicitly: highest business impact + highest likelihood of failure first; communicate clearly to the team what you did NOT get to test, rather than silently under-testing and letting people assume full coverage.

22.11 Mock Exam — Answer Key

Section A

  1. Severity = technical impact of the defect; Priority = business urgency to fix. Example: a homepage typo is Low severity, High priority.
  2. Smoke = broad, shallow check that a new build is stable enough to test further. Sanity = narrow, focused check after a specific fix.
  3. BVA tests values at the edges of valid ranges (min, just below min, just above min, max, just below max, just above max) since bugs cluster at boundaries. Example: age field 18-60 → test 17, 18, 19, 59, 60, 61.
  4. Verification = "are we building it right?" (static, document/spec review). Validation = "are we building the right thing?" (dynamic, executing the software).
  5. New → Assigned → Open → Fixed → Retest → Closed (or Reopened if retest fails); alternate paths: Rejected, Duplicate, Won't Fix.
  6. EP divides inputs into partitions where all values should behave the same; test one representative value per partition to reduce redundant testing.
  7. Regression testing re-runs existing tests to confirm previously working functionality still works after a code change; performed after any change, especially before release.
  8. A test scenario is a high-level "what to test" (one line); a test case has detailed steps, data, and expected results. One scenario often expands into multiple test cases.
  9. Exploratory testing is simultaneous learning, test design, and execution — structured and purposeful, guided by tester experience, distinct from unstructured "ad-hoc" testing.
  10. SDLC covers the whole software development process (requirements through maintenance); STLC is the testing-specific subset of activities (requirement analysis through test closure), which runs in parallel with/within the SDLC.

Section B (sample strong test cases — yours don't need to match exactly, but should hit these categories)

  • TC1 (Positive): Valid current password, valid new password (8-20 chars, has a number), matching confirmation → success message shown, other sessions logged out.
  • TC2 (Negative): Incorrect current password entered → error shown, password NOT changed.
  • TC3 (Negative): New password and confirm password don't match → error shown, password NOT changed.
  • TC4 (Negative): New password has no number → validation error shown.
  • TC5 (Boundary): New password exactly 8 characters with a number → accepted (min boundary).
  • TC6 (Boundary): New password exactly 20 characters with a number → accepted (max boundary) — this is the exact case that exposes the bug in Section C.
  • TC7 (Boundary): New password 21 characters → rejected with validation error.
  • TC8 (Security): After password change, verify old password no longer works for login.

Section C (sample strong bug report)

Title

Change Password form fails silently (no error, no success) when new password is exactly 20 characters
Environment: [fill with your actual test environment]
Preconditions: Logged in as a valid user
Steps to Reproduce: 1) Go to Change Password form. 2) Enter correct current password. 3) Enter a new password exactly 20 characters long, containing at least 1 number. 4) Enter the same value in Confirm Password. 5) Submit.
Expected Result: Password is changed successfully; confirmation message shown; other sessions logged out.
Actual Result: No confirmation message appears, no error message appears, and the password is not actually changed (verified by attempting login with the new password, which fails).
Severity: Major (a valid boundary-length password should be accepted; this silently breaks the feature with no user feedback)
Priority: High
Reproducibility: Always

Section D

1. SELECT * FROM users WHERE YEAR(created_at) = 2025;
2. SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id HAVING SUM(amount) > 3000;
3. SELECT u.name FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL;
4. SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;
5. SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id ORDER BY total DESC LIMIT 3;
6. WHERE filters individual rows before grouping; HAVING filters groups after aggregation — you can't use an aggregate function like SUM() inside WHERE.

23.4 Capstone — Simulated End-to-End QA Cycle

In plain English

Do this in your final week before applying, as a full-dress rehearsal.

Fictional app

"QuickCart" — a small e-commerce web app with: user registration/login, product browsing with category/price filters, a cart, checkout with a mock payment step, and an order history page. Assume a REST API backend and a PostgreSQL-style database with users, products, orders, and order_items tables.

Your task, in order

  1. Requirement analysis: write 3 user stories with acceptance criteria for any 3 of the features above.
  2. Risk identification: list the 3 highest-risk areas of this app and why (hint: payment/checkout involves money — atomicity matters, per Part 8.5's ATM/banking discussion).
  3. Test planning: a short test plan covering scope for this cycle.
  4. Test scenarios: 10 scenarios across the app.
  5. Test cases: expand 5 of those scenarios into full test cases.
  6. Boundary analysis: apply BVA to at least 2 numeric/length-constrained fields (e.g., cart quantity, password length).
  7. Bug reports: write 2 realistic bug reports (invent plausible bugs consistent with the app description).
  8. SQL validation: write 3 SQL queries you'd run to verify data integrity after a checkout (e.g., order total matches sum of order_items, stock decremented correctly, no orphaned order_items).
  9. API testing: design a Postman-style test set (just the list of tests, doesn't need to be executable since this is fictional) for POST /api/orders.
  10. Regression: describe what you'd include in a regression checklist before a release.
  11. Basic performance awareness: name 2 things you'd want load-tested if this app had 10,000 concurrent users (awareness-level, per Part 19.2).
  12. Final QA report: a 1-page summary as if reporting to a QA lead — what's tested, what's risky, your recommendation (ship / don't ship / ship with known issues).

Do this yourself, genuinely, before looking at any model answer approach. This capstone is intentionally close to the shape of a real take-home QA assessment some BD companies use — treating it as a dry run is exactly the point.

Self-check after completing it

did you apply EP/BVA without being told to? Did your bug reports have precise steps and severity/priority reasoning? Did your SQL queries actually target data integrity, not just basic retrieval? Did your final report make an actual judgment call (not just list facts)? If yes to all four, you're genuinely at the "junior-ready" level this guide targets.

What Happens After You Get Hired: The Django Transition Plan

In plain English

This is the part that makes this whole guide make sense as a strategy, not just a QA course. Read this now, but really revisit it once you have the job.

27.1 The core idea

You'll be working full-time as a QA. The realistic hour budget for learning Django alongside a full-time job is roughly 1-2 hours/day on weekdays, more on weekends — call it 10-14 hours/week, similar or slightly less than your current pace since you'll also be adjusting to a new job. At that pace, a focused Django curriculum (roughly 150-180 hours, since backend dev requires more hands-on building than QA theory) takes ~12-16 weeks, comfortably inside your 4-5 month target.

27.2 What you already won't need to re-learn

Because of how this guide was built, you walk into the Django phase already knowing: Python fundamentals through OOP, SQL (deeply — directly maps to Django's ORM concepts), Git workflow, HTTP/REST/API concepts (you'll now be building the APIs you used to test), and JSON. This is a genuinely significant head start most Django beginners don't have — lean into it rather than re-studying these from a "backend dev" book from scratch.

27.3 Rough shape of the Django phase (for when you get there — not now)

  1. Django fundamentals (~25h): project/app structure, URLs, views, templates, settings.
  2. Models & ORM (~25h): this is where your SQL knowledge pays off directly — you'll recognize what the ORM is doing under the hood, which most beginners don't.
  3. Django REST Framework (DRF) (~30h): building the APIs — again, your Part 15-16 knowledge means you already know what a good API should look like from the consumer side, which is a real advantage when designing one.
  4. Authentication & permissions (~20h): directly connects to Part 2.8 and Part 19.3's security awareness.
  5. Admin, forms, deployment basics (~25h).
  6. Testing your own Django code (~15h): pytest/Django test framework — full circle, you'll be writing the automated tests you spent this whole guide learning to design manually.
  7. A real portfolio project (~30-40h): a small but complete Django + DRF app (e.g., a task tracker or small e-commerce backend) — this becomes your backend-dev portfolio piece.

27.4 Practical advice for the transition period itself

  • Don't mention your backend ambitions loudly at your new QA job in the first few months — build trust and do the QA job well first. It's fine (even good) to mention genuine technical curiosity if it comes up naturally, but you don't want to be perceived as already halfway out the door.
  • Being a good QA who understands the backend deeply is not wasted effort even from a pure career-strategy view — QA engineers who can read/write basic backend code and SQL are more valuable, better paid, and it's a completely reasonable, explainable internal growth story if you ever do want to formally move to a hybrid or backend role at the same company, rather than only external job-hopping.
  • When you do start applying for backend roles, your QA experience is a genuine asset, not something to downplay — "I understand what breaks software and how to test rigorously" is a real differentiator for a junior backend dev, and you should say so explicitly in those interviews.
